# Care record identity persistence (bounded storage slice)

`Pet_Belongings` keeps the original 34 columns. Persisted identity enrollment is opt-in through the script property `CARE_RECORD_IDENTITY_WRITES_ENABLED=true`, which should be set only after the copied-sheet validation is complete. With the property disabled (the default), the two optional columns are not appended. If a sheet already has the exact appended pair, ordinary writes preserve its values. With enrollment enabled, the optional `Stay ID` and `Dog ID` columns are appended as columns 35 and 36 only after a deliberate Care write proves that exactly one booking row owns the legacy stay key. That proof checks duplicate/malformed identity headers, duplicate booking keys, stable-ID reuse, malformed stored IDs, and conflicts between supplied and stored identity. Reads never create the sheet or repair its headers.

Belongings, safety summary, profile detail, and media reads fail closed for duplicate Care keys, invalid Care identity headers, invalid IDs on the requested record, or a stored ID that conflicts with the uniquely proven booking. Legacy rows remain compatible in memory only when the booking key is unique. First-match behavior is blocked. One dog may have multiple stays, so Dog ID reuse across separate rows is valid; Stay ID reuse is not.

Writes through the central Care upsert and the active direct safety/media mutation paths prove identity before touching the row. With enrollment enabled, a successful write persists both proven IDs on that same row. With enrollment disabled, existing appended ID values are preserved and a legacy row remains at 34 columns. No open-profile read migrates records, and no bulk migration, deletion, merge, or relabeling is included. Same-key bookings remain unresolved because a legacy Care row does not identify which booking owns its existing content.

Synthetic fixture coverage lives in `tests/care-record-identity-persistence.test.js`. This source change does not establish copied-sheet or production deployment evidence. Release remains backend first, following the controlled sequence in `next-stable-care-record-identity.md`. Validate with the property disabled first, then opt in only on the copied sheet. Production enrollment remains disabled until the copied-sheet evidence is reviewed; backend code may be released with the default-off enrollment switch.

Date or name edits preserve a unique legacy Care row when the validated mutation captures the exact booking Stay ID before the change, the destination booking uniquely matches that ID, the old booking key no longer belongs to a booking, and the source/destination Care rows are uniquely safe. Receipt recovery passes the same verified Stay ID. This compatibility carry-forward does not enroll new identity columns.
