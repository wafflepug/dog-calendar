# Browser CI setup

The Home Guest Portraits job and the browser jobs in `ui-regression.yml` use separate setup steps so a dependency failure or timeout is distinguishable from a test failure. Each job has a 30-minute limit. The browser-cache restore step has a 3-minute limit, npm installation has a 5-minute limit, and Playwright system-dependency and browser setup has an 8-minute limit. Together, these setup steps have a 16-minute limit within each job's 30-minute budget. Browser test steps in Home Guest Portraits each have a 10-minute limit; UI regression browser tests remain bounded by their existing 30-minute job limits. The cache action's post-job save runs outside the restore step and is not covered by its 3-minute timeout.

`actions/setup-node` caches npm's package download cache using `package-lock.json`; it still runs `npm ci` on every job. `actions/cache` stores `~/.cache/ms-playwright` under keys containing the browser set, runner OS, runner architecture, and lockfile hash. The separate `chromium` and `chromium-firefox-webkit` keys keep the Chromium-only Home Guest job from occupying the three-browser UI cache key. The lockfile hash pins each cache to the installed Playwright version and browser revisions; a lockfile change creates a new cache key. There is no broad restore key, so an incompatible browser cache is not restored.

Every run installs Playwright's Linux system dependencies, including on a browser-cache hit. Every run also invokes Playwright's browser installer. It checks the required browser revisions and uses the cached binaries when present, downloading missing binaries as needed. The cache does not guarantee that setup will finish within its timeout; network, package repository, cache, and runner conditions can still affect a run.

If npm or browser setup fails or times out, the workflow summary says that setup failed before the tests ran. The corresponding test step is separate and runs only after setup succeeds. When a workflow has a transient setup failure, inspect the failed setup step and its log first. If the failure is isolated to one matrix group or shard, use GitHub Actions' **Re-run failed jobs** option so passing groups are not repeated. Repeated setup failure should be diagnosed from its logs rather than hidden by an automatic retry loop.
