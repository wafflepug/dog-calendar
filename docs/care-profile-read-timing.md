# Care profile read timing slice

This bounded browser slice measures the directory page in a fresh context (cold) and after returning to the guest list and reopening the same profile (warm). It records only `performance.now()` phase times, resolved backend action names, per-action attempt counts, and local fixture response durations. It does not record URLs, keys, names, phone numbers, notes, or raw payloads.

The live directory timing hook labels application-cache state as `memory`, `saved`, `miss`, or `shared`. `transportMs` measures the client-side Apps Script request round trip, including network transit and response handling. `backendMs` is populated only when the backend supplies its explicit server elapsed duration; it excludes transit. The allowlisted `serverCacheState` reports only `hit`, `miss`, or `unchanged`. Missing or invalid server metadata remains `null`; no guest or request identity is included in the timing sample.

Conditional reads use a retained response only when the existing cache slot is available, the caller's identity predicate accepts its payload, and the cached version, variant, and opaque response tag all match the server's `unchanged` acknowledgement. A missing or mismatched tag (including data rebuilt by another client without a scope-version change) triggers one unconditional read; a second marker is treated as an error. Existing full-payload backend responses remain valid and simply omit server timing fields or response tags. This instrumentation does not add polling, and it cannot separate callback/render work from total read duration.

The synthetic wire-size check serializes an Apps Script-style full response containing 40 directory records and compares its UTF-8 JSON bytes with the metadata-only acknowledgement: 13,517 bytes versus 223 bytes (about 60.6× smaller). This demonstrates the protocol's payload reduction for that fixture; actual savings depend on the number and length of current records.
