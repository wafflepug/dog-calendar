# System Status release attribution

System Status uses `waffle-deployment.json` for the deployed Pages artifact identity. GitHub Pages runs its existing GitHub-managed Jekyll build; the generated manifest supplies the full `site.github.build_revision` and Pages generation time. The page combines that identity with the `waffle-build.json` release name/revision and checks that `assetRevision` agrees with `waffle-release.json.currentRelease`. A mismatch is shown as a warning. The pinned runtime build and retained rollback SHA fields in `waffle-build.json` and `waffle-release.json` remain historical compatibility data and are never used as the current deployed SHA.

Local Python serving does not run Jekyll, so the front-matter source for `waffle-deployment.json` may be returned as non-JSON locally. That correctly appears as unavailable (or uses a labelled local cached value); it does not establish a production deployment failure. Browser checks route a generated manifest fixture because they test the status UI rather than GitHub's build service.

The Apps Script deployment remains separately owned by `.github/workflows/deploy-apps-script.yml`. It creates a deployment identity in the workflow checkout before `clasp push`, then checks the live `get_data_versions` response for the exact workflow SHA, run ID, stable-stay capability, and stay-operation capability. System Status reads that response directly. It shows protocol capability versions separately from the backend commit identity and records when this browser last observed that identity. A successful manifest or health read alone does not verify deployment identity.

For deployment ordering, merge the website changes and let the current Pages source publish its generated artifact. Backend source changes deploy only through the Apps Script workflow. A healthy release claim requires the live Pages SHA and generation time plus the live Apps Script SHA/run identity and both expected protocol versions. The browser does not call authenticated GitHub APIs and does not expose deployment credentials. If a manifest read fails, the page uses only its paired cached SHA, build metadata, and release metadata; cached, stale, offline, and unavailable states remain labelled.

Historical fields such as `latestMergedSha`, `validatedCandidateSha`, `previousStableSha`, `maintenanceCommit`, and the pinned `runtimeBuild` are retained for existing rollback and smoke consumers. They remain visible only in the historical rollback metadata card.

The generated backend file contains only a full commit SHA, source generation time and public workflow run ID. It does not contain a verification timestamp or claim that verification already succeeded. The pipeline checks those fields after deploying; the browser records its own later live observation separately. A manual push of the committed placeholder reports unknown deployment identity. Existing backend business logic is not patched during deployment.

The Release Attribution PR workflow builds with the same GitHub Pages Jekyll action and validates the generated SHA. Production browser smoke now waits for the exact merge SHA instead of treating the historical release label as freshness evidence. The documented Jekyll metadata fields are described in the [official configuration reference](https://jekyll.github.io/github-metadata/configuration/) and [site.github reference](https://jekyll.github.io/github-metadata/site.github/). No repository Pages settings are changed.
